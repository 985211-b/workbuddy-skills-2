Skill 学习笔记（智能体技能）

概念个人解释

Skill（智能体技能）是把"怎么做某类事"的完整知识打包成一个文件夹，让 AI 助手按需加载、自动复用的能力模块。

一个 Skill 最小只需要一个 SKILL.md 文件（YAML 元数据 + 操作指令正文），复杂时可以带上脚本、模板、参考资料。Anthropic 官方的类比最传神：给智能体写 Skill，就像给新员工写入职手册——你不需要为每个岗位定制一个"专门的人"，只需要把老员工的经验写成手册，谁来了都能照着干成专家。

最妙的一点：这个概念你已经用了两天了。仓库里的 ai-concept-structured-learning/SKILL.md 就是一个真 Skill——你丢一句"学习 MoE，偏落地"，Agent 就按它的五步流程执行。这份笔记本身就是 Skill 机制的活案例。

行业时间线：Anthropic 2025 年 10 月推出 Agent Skills，12 月将其发布为开放标准（agentskills.io，捐给 Linux 基金会旗下的 AAIF）。48 小时内 Microsoft 和 OpenAI 跟进支持，到 2026 年 3 月已有 32 个工具采用 SKILL.md 格式（包括 Gemini CLI、Cursor、GitHub Copilot、Codex CLI）——写一次，处处能跑。

核心机制与组成

Skill 的灵魂设计是渐进式披露（Progressive Disclosure）——三层按需加载，本质是对上下文窗口的精细管理：

层级加载时机内容Token 代价
L1 元数据启动时常驻YAML frontmatter 里的 name + description每个 Skill 约 50~100 tokens
L2 指令正文判断相关时才读SKILL.md 正文：流程、规则、示例500~5000 tokens
L3 资源与脚本执行中被引用时参考文档、模板、可执行代码近乎无限（脚本代码本身不进上下文，只返回结果）

运行逻辑拆解：

  • 发现：Agent 启动时只扫描所有 Skill 的元数据，生成一份轻量"技能目录"注入系统提示。装 500 个 Skill 也只占几万 token 的目录空间，细节一概不加载。
  • 触发：用户请求匹配某个 description 时，Agent 读取完整 SKILL.md 进上下文——只有这一份被加载。
  • 执行：正文引用到脚本就直接跑代码拿结果（脚本内容永不进上下文）；引用到参考文档才读参考文档。任务结束后厚重内容可从上下文移除，只留结果。

为什么这个设计如此关键：如果没有渐进式披露，给 Agent 挂 50 个完整定义的技能会同时打爆三个瓶颈——上下文窗口溢出、注意力稀释导致选错技能/填错参数（幻觉）、每轮对话重复输入数万 token 导致成本失控。渐进式披露把这三座山全部搬走，这就是 Skill 能规模化到企业级（Uber 500+、Cognizant 35 万人部署）的架构基础。

与相邻概念的精确分界（这是最容易混的部分）：

维度Skill工具/函数调用MCP系统提示
本质知识/程序性经验包确定性的原子动作连接外部系统的协议常驻的一段文字
决策粒度用哪个技能、何时、怎么用用哪个工具、何时提供工具通道无（永远在场）
加载按需schema 每轮全量在场服务器常驻每轮消耗
通俗说法"知道该怎么做好这件事""手上有这个动作""接上了外部系统""人设说明书"
一句话记住：Tool 是手，MCP 是外部接口，Skill 是打法手册。生产级 Agent 三者全用：系统提示定基线行为，MCP 连外部数据，Skill 沉淀"怎么用好"的组织经验。

实际应用场景

Uber 的 Skill 生态从 2 个长到 500+（Anthropic 官方直播访谈一手资料）

背景：Uber 有 200+ 微服务、数千名工程师。2025 年 10 月，一位平台工程师深夜自建了一个内部 Skill 市场，里面只放了 2 个 Skill（CI 日志分类、代码评审修复）——没有立项、没有审批、没几个人知道。到年底缓慢长到约 20 个；2026 年 1 月迎来拐点：工程团队集体经历"aha 时刻"，像多米诺一样扩散；到 3 月，精选市场 200+ Skill，加上团队和个人市场总计 500+，访谈前一周就新增 20 个。

执行流程（完整体现机制设计）：

  1. 渐进式披露支撑规模化：数百个 Skill 常驻的只是元数据目录，工程师打开 Claude Code 时零配置加载精选市场，没有上下文爆炸。
  2. 两层市场治理：黄金市场（默认体验）——每个 Skill 入库须过三道关：人工代码评审、CI/CD 流水线、LLM-as-Judge 自动评估（按预期输入输出自动测试，达标才放行），目标控制在约 100 个核心 Skill，宁缺毋滥；个人/团队实验市场——低门槛快速实验，URL 即分享，验证有效后"毕业"进黄金市场。设计哲学：核心体验严格把关 + 边缘自由创新。
  3. 每个 Skill 有明确 Owner（通过 CODEOWNERS 机制），文档和性能保障齐全。
  4. killer 应用是分层代码评审：不是一个"快速评审"按钮，而是一族 Skill——日常小改动走快速通道，高风险 PR 走深度审查，不同强度匹配不同场景。

落地效果：500+ Skill 覆盖整个开发生命周期，且增长完全自驱（"一周新增 20 个"），无需管理层推动。同行可对标数据：IG Group 分析团队用 Skills 每周省 70 小时、3 个月达到 ROI；AutoScout24 建成跨 Claude Code/Codex 通用的内部 Skill 市场，实现"写一次、两种 Agent 都能装"。Uber 的经验浓缩成一句：最好的 Skill 往往来自某个工程师深夜的发现，而不是中心化团队的决策——但前提是有人把质量闸门守好。

易混淆问题与使用边界

常见误区

  1. "Skill 就是保存下来的 Prompt"——差三个量级：Prompt 是一段文字，用完即弃、无版本、无复用；Skill 是文件夹：指令 + 示例 + 参考文档 + 可执行代码，可 Git 版本管理、可团队共享、可跨平台（开放标准）移植。判断标准很简单：一段话能说清的用系统提示；需要检查清单、示例和辅助脚本的，做成 Skill。
  2. "Skill 会取代 MCP/工具"——层级不同，是配合不是竞争：Block 团队的总结最精准："MCP 给予能力，Skill 教会怎么用好这些能力"。MCP Server 把你的 Postgres 连上来提供 run_query 工具，但怎么针对你的表结构写安全高效的 SQL——这是数据库查询 Skill 干的事。生产架构里两者叠加使用。
  3. "装得越多越强"——恰恰相反：业界共识"别一次建一堆 Skill"：描述含糊会导致触发失灵（YAML description 是路由的唯一依据，写弱了 Agent 就会漏触发）；重复冲突的 Skill 会让 Agent 选择困难。Uber 把黄金市场刻意控制在约 100 个核心 Skill，AutoScout24 用 CODEOWNERS + 质量闸门防"技能蔓延"。
  4. "Skill 是确定性的"——不是：Skill 由 LLM 解释执行，天然带非确定性。需要保证结构的环节，应把关键部分做成 Skill 里捆绑的脚本（代码确定性执行），而不是纯自然语言指令。这正好呼应 L3 层的设计：指令管灵活，代码管可靠。

使用边界（它做不到的事）

  • 不能保证自身安全：Skill 可含可执行代码，恶意 Skill 或被注入恶意指令的文件可能执行与声明不符的操作、外泄数据。Anthropic 官方文档明确警告提示词注入风险，且"只用可信来源"的执行责任落在用户身上。装第三方 Skill 等于给 Agent 装第三方代码，必须走安全审查——这正是企业级部署中治理缺失导致失败率高的头号原因（McKinsey 数据：74% 的部署一年内达到 ROI，但只有 10% 能规模化过 PoC）。
  • 不能自动保持新鲜：它记录的是编写时刻的知识，流程变了（Jira 字段改名、API 改版）Skill 就开始输出过时结果。没有 Owner 和更新机制的市场会迅速退化为"数字废墟"（重复、过时、互相冲突）。维护成本是真实存在的：业界实测每个 Skill 有 2~4 小时的月度维护成本。
  • 不能替代判断：它把"怎么做"编码成文档，但"该不该做、什么时候不适用"仍依赖调用它的 Agent 和人的判断。一个包装精良的错误流程会被 Skill 高效地重复放大——复用性是把双刃剑：好经验规模化的速度有多快，坏经验规模化的速度就有多快。
