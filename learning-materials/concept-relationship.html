概念关系：LLM Context × Agent × Skill

本页是四份学习笔记的"合龙"：说明 大模型上下文（LLM Context）、Agent、Skill 三个概念如何互相咬合，重点回答两个问题——上下文如何决定 Agent 的工作质量，以及 Skill 如何把任务经验沉淀成可复用的资产。

一、一句话总览

Agent 是循环决策的"人"，上下文是它每次决策时眼前唯一的"桌面"，Skill 是把成功经验固化后、可以随时摆上桌面的"操作手册"。

三者关系可以压缩成一条链：Skill（知识资产） → 注入 → Context（单次推理的视野） → 驱动 → Agent（循环决策） → 执行结果与新经验 → 反哺 → Skill（再沉淀）

三、上下文如何影响 Agent 的工作

这是理解三者关系的第一把钥匙：Agent 的每一次"思考"都是一次无状态的 LLM 推理调用，上下文就是它全部的世界。模型不会记得上一轮调用，它之所以表现得"有记性、有目标、有方法"，完全是因为编排层把相关信息重新拼进了这次的上下文。

3.1 上下文决定了 Agent 的三个边界

  1. 知识边界：它知道什么。系统提示里的角色与规则、注入的记忆、对话历史中的事实——不进上下文，对 Agent 就等于不存在。
  2. 能力边界：它能做什么。工具定义（函数签名、参数说明）必须写进上下文，模型才"知道有这个工具可调用"。上下文里没有的工具，Agent 再强也用不了。
  3. 行为边界：它怎么做。约束、风格要求、步骤规范都在上下文里。上下文写"先确认再删除"，Agent 才会先确认；写丢了，它就可能直接删。

推论：Agent 的上限由模型决定，下限由上下文工程决定。同一个模型、同一个任务，上下文组织得好坏，产出质量可能天差地别——这正是 "Context Engineering"（上下文工程）作为一门实践学科兴起的原因。

3.2 Agent 循环中上下文的动态膨胀

Agent 不是一次调用，而是"推理 → 调用工具 → 把工具结果追加进上下文 → 再推理"的循环。这意味着上下文随步数单调增长：

问题成因对 Agent 的影响对策
关键信息丢失早期指令被长历史淹没忘记约束，重复犯错或偏离目标关键规则放系统提示；定期重申目标

核心心智模型：把上下文当作稀缺资源来做预算管理。Agent 的编排层本质上是"每轮为模型组装一个最优工作现场"的工程师——什么进、什么出、什么摘要、什么落盘，这些决策统称上下文工程，直接决定 Agent 的可靠性与成本。

四、Skill 如何沉淀可复用的任务知识

第二把钥匙在于补齐链条的最后一环：LLM 无状态、Agent 会话结束即"失忆"，那么"这次任务做得漂亮的方法"如何留下来？答案是 Skill。

4.1 没有沉淀时的困境

假设某次你反复调试后总结出"同步这个仓库要先走 API 通道、git 要设 autocrlf=false"——如果不沉淀，下次开新会话，Agent 从零开始，把同样的坑再踩一遍。上下文撑不过一次会话，Memory 适合存"事实与偏好"（是什么），却不是表达"操作流程"（怎么做）的最佳载体。

4.2 Skill = 程序性知识的固化

知识类型典型载体例子特点
陈述性知识（是什么）Memory / 文档"用户的仓库地址是 X""他偏好简洁回复"事实条目，随取随用
程序性知识（怎么做）Skill"同步 GitHub 的五步流程、脚本模板、坑位清单"结构化流程 + 可执行资源，可被触发加载

Skill 把一次成功执行所依赖的流程步骤、判断标准、脚本模板、注意事项打包成标准格式（元数据 + SKILL.md 指令 + 资源文件），从而实现：

  • 跨会话复用：新会话中只要任务匹配触发条件，老经验立即上线；
  • 可版本演进：Skill 是纯文本/代码，可 diff、可回滚、可多人协作；
  • 渐进披露、按需占用上下文：平时只有几行元数据常驻索引；命中任务才加载正文；重资源（脚本、参考文档）只在用到时读取——把第三节说的"上下文预算"花在刀刃上。

4.3 沉淀闭环：从经验到资产

4.4 三层结构与上下文预算的配合

层级内容何时进入上下文占用
1. 元数据name + description（触发条件）常驻（进入技能索引）几十 Token
2. SKILL.md 正文流程指令、判断标准、注意事项任务命中时加载数千 Token
3. 资源文件脚本、模板、参考文档执行中按需读取几乎不占（在文件系统里）

这个分层正是第三节"上下文稀缺"约束下的最优解：用最小的常驻成本换取最大的按需能力——这也是 Skill 区别于"把一篇长教程永远塞在系统提示里"的根本所在。

五、三者协同：一次任务的完整解剖

以"帮我同步代码到 GitHub"为例，把三个概念放到一条时间线上：

时刻发生的事涉及概念
t0 触发用户说"同步到 GitHub"，编排层匹配到 Skill 的 description → 决定加载Skill（第 1 层：元数据路由）
t1 装配SKILL.md 正文 + 相关工具定义 + 系统提示 + 对话历史拼成推理上下文Skill → Context（注入）
t2 决策LLM 基于上下文判断：先试 push，失败则走 API 通道（步骤写在 Skill 里）Context → Agent（视野决定动作）
t3 行动调用工具执行；工具返回结果被追加进上下文，进入下一轮推理Agent ↔ Context（循环膨胀）
t4 完成任务结束，本次上下文消失；但若流程有改进，可更新 Skill 版本Context 消亡，Skill 沉淀
t5 下次新会话遇到同类任务，Skill 重新注入，经验无损耗复用Skill 的复利

六、常见误区辨析

误区一："上下文窗口很大（200K+），所以不用担心塞满。" 窗口大 ≠ 注意力好。长上下文中部的信息召回率显著下降（"迷失在中间"效应），且每轮全量历史计费。预算思维不因窗口变大而过时。

误区二："Skill 是模型内置的能力。" Skill 不改变模型权重，它只是"在合适的时机，把正确的操作知识放进上下文"。模型还是那个模型，变的是它眼前桌面上的手册。

误区三："有了 Memory 就不需要 Skill。" Memory 回答"是什么"（事实、偏好），Skill 回答"怎么做"（流程、方法）。让 Agent 从一堆事实记录里现场重新推导操作流程，既不稳定也不经济。

误区四："Agent 失败是模型不行。" 实践中大量失败源于上下文问题——该注入的没注入、工具结果没裁剪、约束被长历史冲掉。排查 Agent 问题时，第一现场永远是"这次推理的上下文里到底有什么"。

七、记忆锚点

  • 桌面 Context 是 Agent 眼前的桌面：桌面上的东西决定它能看见、能做什么。
  • 循环 Agent 的记忆是错觉：每轮都靠重新拼装上下文续命，历史只增不减，需要预算管理。
  • 手册 Skill 是可版本化的 SOP 手册：把一次做对的方法固化，让下次从 80 分起步。
  • 闭环 三者构成飞轮：Skill 注入 Context → Context 驱动 Agent → Agent 产出经验 → 经验升级 Skill。
